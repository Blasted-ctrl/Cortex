# Demo media

Everything here is generated by scripts in this repository, so it can be checked
and re-recorded instead of trusted.

| File | What it shows | Made by |
|---|---|---|
| `cortex-demo.mp4` | The full story: open a project, run it on the 3D board, run the firmware tests, see a real failure with its evidence, type the fix, rerun until everything passes | `npm run demo:video` |
| `cortex-teaser.gif` | Three short clips from the same recording: the 3D board, the failing evidence, the passing rerun | `npm run demo:video` |
| `cortex-demo.json` | Provenance for both: commit, host, compiler, the real duration of every fast-forwarded wait and both sets of test results | `npm run demo:video` |
| `firmware-test.gif` | The headless CLI running the three example scenarios | `npm run demo:terminal` (VHS) |

`npm run demo:record` rebuilds the app and regenerates all of it.

## What is real and what is drawn on top

[`scripts/demo/record-demo.ts`](../../scripts/demo/record-demo.ts) drives the actual
desktop app with Playwright's Electron API and records the window. The project is a
temporary copy of the example heater controller in which only the ADC range check is
missing ([`fixtures/missing-range-check.ino`](../../examples/firmware-testing/fixtures/missing-range-check.ino)),
so the failure in the video is the real test runner catching a real bug. Clicks,
the panel resize and typing the fix are real input events. The script checks the
results at each step and refuses to render if they differ from the story, for
example if anything other than `invalid-input` fails on the buggy sketch or the
evidence caption no longer matches the report.

Added on top, all by the script:

- Captions at the top of the window and a drawn cursor (Playwright videos have no pointer).
- Fast-forwarding while g++ compiles and while the fix is typed. An orange badge shows
  the real elapsed time during each stretch, and `cortex-demo.json` lists what each one
  was, how long it really took and how long it is shown.
- Folder selection: the OS folder picker cannot be recorded, so the script answers it
  with the demo project. The app's own Open folder button and loading path still run.
- Camera zoom on the 3D board: the wheel events are dispatched on the canvas and
  handled by the same OrbitControls listener a physical mouse wheel reaches.

The recording uses a throwaway Electron profile. If Cortex's managed Arduino CLI
already exists in the normal profile, it is put on PATH so the throwaway profile
does not download board tools mid-recording; board tools play no part in the demo.

## Re-recording

You need a built app (`npm run build`), a host `g++` and `ffmpeg` on PATH, and a
display (on Linux, run under `xvfb-run`). Close heavy applications first: the app
compiles each scenario with g++, and Cortex's 60-second compile limit can be reached
on a saturated CPU, in which case the script stops instead of recording a broken run.
On Windows: `winget install Gyan.FFmpeg charmbracelet.vhs tsl0922.ttyd`.

`DEMO_KEEP=1 npm run demo:video` keeps the raw recording, the app log and any
failure screenshot in a temporary folder and prints its path.

The terminal GIF is played back at 3x; most of the real run is g++ compiling each
scenario. On Windows the tape uses PowerShell; see the comments at the top of
[`scripts/demo/firmware-test.tape`](../../scripts/demo/firmware-test.tape) for bash.

An older, hand-recorded walkthrough of the same failure and fix lives in
[`docs/demos`](../demos/README.md).
